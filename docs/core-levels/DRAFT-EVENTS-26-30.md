## Language and observation contract

Read the complete cached G8 mixed-tense and G9 perfect/past sources first. The exact G7 present/past page was missing locally; its ID was discovered and its canonical page fetched through Workbook, then retained in the ignored source cache. [Source provenance](events-26-30-source-provenance.json) records the files and hashes.

Past simple reports an event or finished period. It does **not** say that a machine reversed, lost power, remains parked or changed permanently. Present perfect can connect an event with the present discussion; it is **not** a mechanical latch. Every result statement below therefore has a separate truthful current-state observation. Both tense forms can describe the same genuine event. A meaningful contrast changes an explicit requested state, allocation or destination in the same fixture; merely replacing *opened* with *has opened* cannot invert the puzzle.

**NEW CAPABILITY, pending root + Art: bounded read-only machine journal.** A small optional in-world panel could show the last 6–8 actual transitions, their room-elapsed timestamps and a separate NOW line. It starts empty, never with invented prehistory. An `arrived`, `opened`, `closed`, `pad pressed/released`, `beam connected/lost` or `latch caught` row must follow the corresponding actual physical state/contact transition, not merely a command, desired target or start-of-animation cue. The existing event producer names need audit: a `shutter-open` cue can precede full clearance, so it alone cannot truthfully generate “The shutter has opened.” A real stopped-dock predicate must precede “has arrived.”

The journal does not control completion, record a grammar answer, fabricate an earlier trial or hide the live machine. During movement it says MOVING, not AT DOCK because an old arrival exists. At a disconnected receiver it says DARK even if a prior connection is listed. Retry begins a new visible attempt; retained archival rows, if offered, are explicitly separated from the current attempt. Pending this capability, observe the real animations/lights directly and withhold event-reading verification. Do not substitute a static history board.

The candidate missions below are true instructions on a fresh load. Perfect/past report examples appear **only after the player or automatic machinery actually causes the stated event**; no instruction presupposes an unobserved completed test.

## 26 · After the Test — identify an actual past event

**Base:** “Run the test and retrieve the cube. Switch the test off, then use the gate that opened during the test.”

**Same-fixture contrast:** “Run the test and retrieve the cube. Switch the test off, then use the gate that remained closed during the test.”

**Physical problem:** An enclosed observation foyer faces two real opaque gates, A and B. TEST powers an actual periodic pulse that opens A; B remains closed. The open A alcove contains the cube needed at the common MANUAL POWER pad. Retrieval makes the test useful, rather than an unrelated grammar countdown. Test mode electrically isolates the independent manual A/B routes. A real opaque console cover opens only with MANUAL POWER present and TEST off, so fresh-state manual switches cannot be preselected through the cover. Both manual switches start off. When the player carries the cube out and switches TEST off, **both actual gates close**. Current appearance no longer identifies which gate opened.

**Ordinary-input causal chain:** Use visible E on TEST → watch a real full-clearance pulse → enter/retrieve ordinary cargo and return safely → switch TEST off → observe both gates fully closed → release the cube on MANUAL POWER → use the independent A or B route control identified by the completed test event → walk through that real gate to its corresponding destination. A linked white route may help retrieval/return, but no inferred panel or invisible teleport bypass is promised before an inspected target.

**Event/current reading:** The bounded board starts blank. It records actual full opening/closure of A within the interval marked by the player's real TEST on/off transitions, and shows both current gates CLOSED after switch-off. For B, “remained closed” requires its actual closed pose throughout the observed interval; merely never reaching full clearance is insufficient. Incomplete/truncated observation must say UNKNOWN rather than infer a negative event. This is a truthful read-only event summary, **not** a completion flag or a fabricated prehistory. The past clause selects A versus B while their current state is identical; past tense alone does not imply any subsequent reversal or closure. The explicit switch-off action and actual circuits cause closure.

**Wrong/recovery/outcome:** Opening B under the base instruction is a genuine wrong-route arrival; it grants no requested unlock, but the player can walk back, close/reselect the controls and take A. Reverse that consequence under the contrast, with identical fixture and test response. The console and cargo remain reachable; no past mistake invalidates later correction. A clever correct physical arrival without the test remains accepted—there is no `usedTest`, minimum pulse count or cargo-identity win gate. If no real test was observed, the journal stays blank and no event-identification evidence is claimed. Target/native/UI review must prove both-currently-closed state, true A-only test clearance, real covered controls, safe retrieval, both routes and return.

## 27 · Release and Reuse — a real latch versus maintained power

**Base:** “Release the cargo latch. Move the power cube to LIFT and reach the balcony through the open hatch.”

**Same-fixture contrast:** “Keep the inspection receiver powered. Leave the cube on POWER and use the inspection passage.”

**Physical problem:** In a compact cargo vault, one receiver actuates a mechanically latched cargo hatch and a separate continuously powered inspection leaf. After an actual release the visible hatch catch remains engaged; the inspection leaf still follows present receiver power. Reusing the cube on LIFT supplies a real balcony lift through the released hatch. Leaving it at POWER supplies the other physical route. Use the existing latch circuit, with an actual readable catch; do not introduce a hidden “has opened” win variable.

**Ordinary-input causal chain:** Put cargo or the player on POWER → route the beam → watch the hatch physically release/catch → remove pressure and see the inspection leaf close while the hatch stays open → place cargo on LIFT → use the freed route. Contrast maintains the original beam and walks through inspection. Either ordinary cargo identity, or another physically equivalent pressure method, remains valid.

**Event/current reading:** “The hatch has opened. NOW: HOLD-OPEN CATCH ENGAGED” pairs an actual completed opening with its independently observable retained result. “The inspection door opened at 00:12. NOW: CLOSED” can simultaneously be true. Persistence comes from the catch and circuit, not from the perfect tense.

**Wrong/recovery/outcome:** A player who removes continuous power cannot pass the now-closed inspection leaf; replace pressure and restore the beam. The hatch does not secretly reset because the player experimented. Test both real results before using the perfect report as a reading exercise.

## 28 · Freight Returned — past arrival versus current receiving pressure

**Base:** “Make a delivery, then reverse the belt. Return the cube to the receiver it left on that trip. Keep that receiver pressed and use its transport.”

**Same-fixture contrast:** “Make a delivery, then reverse the belt. Leave the cube at the receiver it has just reached. Keep that receiver pressed and use its transport.”

**Physical problem:** A T-shaped enclosed freight depot has a sealed reversible cargo conveyor with flush receivers at its two ends. Initial fixed direction sends cargo to STORE; actual STORE pressure releases a visible latch on the reverse-control cover. That delivery thus grants real access to reversal, rather than an unrelated history count. STORE pressure powers a horizontal carrier across a dry channel; SERVICE pressure powers an opposed vertical lift to a recessed maintenance bay. The player reaches the control booth through portals. Unlike two compass doors at the belt ends, the choices produce different transport and spatial plans. End stops retain ordinary cargo physically; both destinations and all circuits are fixed under the language change.

**Ordinary-input causal chain:** Enter the real booth → actual first STORE arrival releases the covered direction control → stop/reverse/restart → the same cargo leaves STORE and actually reaches SERVICE. Both texts explicitly request this first reversal. Base then explicitly says *return*, selecting the receiver it departed from; contrast says *leave*, selecting its current receiving pad. Correct the physical allocation, keep actual pressure and take the corresponding transport. The journal helps identify the departure/arrival relationship; the current pad alone no longer answers both instructions. No delivery count substitutes for a current pressed pad, and no `reversedOnce` win condition is added. A clever correct physical arrival without this demonstration remains accepted, with event-reading evidence withheld.

**Event/current reading:** Once actual cargo arrives, “The cube has reached STORE. NOW: STORE PRESSED” is truthful. After reversal, the old “STORE received the cube at 00:14” remains a past fact while NOW says EMPTY. The present state must visibly brake its carrier until pressure is restored. Do not print a false “has not arrived” merely because cargo later departed.

**Wrong/recovery/outcome:** Taking the other physical machine reaches the wrong bay without unlocking this objective. Both routes have a safe return cycle or real catch return. A lost pad during motion brakes at the actual pose and resumes without a phase jump. Verify arrival/event versus maintained pressure, not “past tense means reversed.”

## 29 · The Parked Link — arrival does not mean still parked

**Base:** “Park the lift at TRANSFER. Cross its deck to the archive.”

**Same-fixture contrast:** “Bring the lift to LOADING. Ride it to the inspection balcony.”

**Physical problem:** A three-stop lift in an enclosed split mezzanine serves LOADING, TRANSFER and INSPECTION. At TRANSFER its real deck completes a horizontal gap between two archive walkways. At INSPECTION it reaches a separate balcony. Stopped alignment opens actual dock leaves; selecting a stop or passing its height does not. A bounded well and generous existing-style stairs return to loading. Neither a decorative guide nor the shaft top forms a walkable substitute.

**Ordinary-input causal chain:** Observe current deck position → use the visible E control → wait for the actual stopped pose → either cross the parked deck or board for ascent. Calling the lift away removes the physical archive link even though its earlier arrival remains recorded. If an existing stair route lets the player park the lift without riding, that equivalent remains valid; no ride/history counter is required.

**Event/current reading:** At genuine arrival, “The lift has arrived at TRANSFER. NOW: STOPPED” describes the useful current result. After another E command produces actual departure, “The lift arrived at TRANSFER at 00:21. NOW: MOVING” prevents treating the old event as current support. Never update the arrival report on destination selection alone.

**Wrong/recovery/outcome:** Boarding late waits for another trip; a departure before crossing exposes a real gap and safe catch recovery. The test must inspect the capsule/deck seam, real stopped flag and wrong dock, not award an unlock from an arrival message. Reading outcome is completed arrival plus independent current location/motion.

## 30 · Reconnect the Supply — transfer after an interruption

**Base:** “Connect the gallery receiver. Put the cargo on the gallery button and leave the receiver lit.”

**Same-fixture contrast:** “Leave the gallery receiver dark. Put the cargo on SERVICE and use the inspection return.”

**Physical problem:** An enclosed U-shaped optical freight route gives one portal pair two real jobs. A momentary optical connection releases a visible latched cargo access. The player can then relink that same pair to transport cargo around an opaque return bend; doing so genuinely interrupts gallery power. Once cargo is delivered, a suitable link restores the gallery receiver. Current receiver power AND remote gallery pressure drive the final lift/door. SERVICE pressure AND gallery darkness instead open the lower inspection return. The already released cargo hatch persists because of its catch, while gallery transport still needs live power.

**Ordinary-input causal chain:** Create an actual beam connection → observe the hatch release → relink and carry ordinary cargo through the real aperture → observe actual connection loss → place cargo on the requested pad → restore or deliberately leave dark the optical route → follow the corresponding real transport/return. A momentary interruption is recoverable; the mission does not say “never interrupt,” so do not introduce an unbroken-history gate.

**Event/current reading:** The journal can record “The gallery receiver connected at 00:10,” then actual loss, then “Gallery power has returned. NOW: LIT.” The return report requires a genuine current lit transition after an observed loss; otherwise use “The receiver is lit.” It is a read-only account of what happened, never an extra completion condition or a forced three-toggle chore. A player who finds a physically equivalent route without interruption is accepted. The fresh-load mission says *connect*, so it does not falsely presuppose a previous connection.

**Wrong/recovery/outcome:** Old connection history cannot move a currently unpowered lift. Restore the visible link or correct the actual cargo pressure; the released access and safe lower loop keep both recoverable. This transfers event/current-state reading into spatial portal planning, without new characters or invented repair animations.
